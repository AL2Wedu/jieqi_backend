## 1. 我的设计判断(回答"你认为应该如何")

你的方案方向正确(卖菜变成玩法,AI 自然语言议价),但有 **4 个必须补的缺口 + 3 个建议**:

### 1.1 缺口①:deal 布尔语义不完整(必须修正)
> 你定义:"AI 抉择,布尔值,选择是否成交,决定了对话的结束"。

按字面,deal=false 时对话也结束 —— 那**讨价还价只有一轮**,砍价玩法不存在。修正为:

- `deal=true` → **成交 + 会话结束**(AI 接受玩家报价)
- `deal=false` → **对话继续**(客人摇头还价),由以下任一条件结束:
  - 玩家 `accept` 接口接受 AI 当前报价(成交)
  - 玩家 `cancel` 赶客(不成交)
  - 轮次上限 `guest.max_turns`(默认 8)→ 强制结束(AI 失去耐心离开,**不自动成交**,玩家若想成交需在最后一轮前 accept)
- 会话字段 `status: bargaining / done / closed / cancelled` 明示状态,前端据此渲染"离开/成交/继续谈"按钮。

### 1.2 缺口②:服务端必须权威校验 AI 期望价(防作弊)
LLM 可被 prompt 注入/幻觉报出天价或负价。成交价**以服务端校验后为准**:
- `offer`(AI 当前报价)必须 ∈ `[市场价 × price_floor, 市场价 × price_ceil]`(默认 0.5~1.5,可配);越界 → 截断到边界。
- `accept`/`deal` 结算用**服务端校验后的 offer**,不用 LLM 原始数字。
- 玩家喊价本身不限制(自由谈),但成交价永远落在区间内 → 无法刷钱,讨价还价的意义是往区间上沿谈。

### 1.3 缺口③:上下文管理用 DB 表(当前无 Redis)
每会话存表:会话表(目标菜/客人/心理价位区间/当前报价/轮次)+ 消息表(全部轮次)。上下文注入 = 系统角色卡 + **最近 N 条**(默认 12 条,超长截断)+ 当前消息。会话结束后保留历史(可做复盘/管理端查看),不删除。

### 1.4 缺口④:LLM 成本控制(每轮都花钱)
- 每玩家**同时最多 1 个活跃会话**(`GUEST_BUSY`)
- `start` 冷却 `guest.cooldown_seconds`(默认 30s,`GUEST_COOLDOWN`)
- `max_turns` 默认 8;AI 调用超时 15s;JSON 解析失败重试 ≤1 次,再失败给兜底话术(不算轮次?算——防刷)
- 用量自动进现有 `ai_usage`(复用 `_record_usage`)

### 1.5 建议①:客人模板配置化(data/guests.json)
名字池 + 性格(爽快/抠门/犹豫)+ 出价系数区间(如爽快 0.9~1.2,抠门 0.6~0.9)+ 开场白模板。**零代码加客人**;AI 心理价位 = 市场价 × 随机系数(会话创建时固定,存 `target_min/target_max`)。同时支持管理后台临时开关(`guest.enabled`)。

### 1.6 建议②:保留旧快速卖出接口(双轨)
`POST /v1/shop/crops/{id}/sell`(直接市场价,管理/紧急用)保留;结算逻辑抽公共 `_settle_sale` 供两处复用(先扣正常后扣枯萎、账本、余额)。

### 1.7 建议③:mood 由 prompt 规则驱动 + 服务端枚举校验
mood ∈ `plain / happy / sad / confused`(中文:普通/开心/失望/疑惑)。prompt 规定规则(报价高于心理价→happy;低于→sad;重复报价→confused),服务端校验枚举,非法值兜底 `plain`。

### 1.8 数量语义
一次会话卖 **1 份**(1 株收成),保持简单;quantity 留作后续扩展。

## 4. 系统 Prompt 与 JSON 格式化

### 4.1 系统 Prompt 结构(ai_guest_service 内构建)
```
你是<名字>,一位<性格>的客人,来买玩家的<菜名>。
市场参考价是<base_price>,你的心理价位是 <target_min>~<target_max> 金币。
规则:
1. 用自然口语讨价还价,每次回复必须同时给出你的报价 offer(金币整数)。
2. mood 只能取 plain/happy/sad/confused:玩家报价高于你心理价→happy;低于→sad;重复纠缠→confused。
3. deal 表示"是否接受玩家当前报价成交":接受→true(回复也要表达成交意愿);不接受→false(继续还价,可小幅让步)。
4. 只输出一个 JSON 对象(不要 markdown 代码块,不要多余文字):
{"reply_text": "...", "guest_name": "<名字>", "mood": "plain|happy|sad|confused", "offer": <整数>, "deal": true|false}
```

### 4.2 调用与解析管线(ai_guest_service._ask)
1. 组装 messages = [system 角色卡] + 最近 N 条历史(截断到 context_messages)+ [user 当前话术]
2. 调 `ai_service.chat`(透传,model 用全局配置;上游支持则加 `response_format={"type":"json_object"}` 增强约束 —— 由 `guest.json_retries` 控制重试)
3. 解析:正则提取首个 `{...}` 或 json 块 → `json.loads`
4. 校验:`reply_text` str 非空;`mood ∈ 枚举`(非法→plain);`offer` int 且 ∈ [floor, ceil] × base_price(越界→截断);`deal` bool
5. 解析/校验失败 → 重试 ≤ json_retries(重试时 system prompt 追加"必须输出合法 JSON")→ 仍失败 → 抛 `GUEST_AI_RESPONSE`(前端显示兜底文案,会话不坏)
6. 成功 → 记消息(role=guest, reply=原始 JSON)+ 更新会话(offer/turns/mood)

### 4.3 状态机(chat 内)
```
bargaining --deal=true--> done(结算,按校验后 offer)
bargaining --turns >= max_turns--> closed(不成交,AI 离开)
bargaining --用户 cancel--> cancelled
bargaining --用户 accept--> done(结算,按当前 offer)
```

## 9. 追加需求:背包道具可卖(saleable 属性)

> 用户追加:背包物品增加"是否可卖"属性。现状:Item 已有 `sell_price`(18 道具全部配置低价回收价,如种子 25 买/5 卖),但无开关字段、无出售接口、背包/商店响应不暴露卖价。

### 9.1 设计

**数据**:Item 表加 `saleable: bool default True`(迁移:幂等 ALTER `items ADD COLUMN saleable BOOLEAN DEFAULT 1`)。

**可卖判定**:`saleable=True` **且** `sell_price` 非空 → 可卖;否则拒绝(`ITEM_NOT_SALEABLE`)。

**价格**:回收价 = `sell_price × quantity`(sell_price 本身就是管理后台配置的回收价,不再加系数,避免重复配置)。

**出售途径(与 AI 客人解耦)**:独立快速回收接口 `POST /v1/shop/items/{item_id}/sell`(按 sell_price 立结),AI 客人聚焦菜品(收成仓作物);若后续想让客人也收道具,再扩展 guest 会话目标类型(开放问题 #7)。

**响应面**:背包 `GET /v1/player/inventory` 每项加 `sell_price`(null=不可卖)与 `saleable`;商店 `GET /v1/shop/items|state` 加 `saleable`(前端"卖"按钮 + 回收价展示)。

**结算**:扣 UserItem 数量(0 则删行)→ 加金币 → `coin_transactions`(reason=`item_sell:<code>`)+ `item_transactions`(审计扣减,reason 同上)。
